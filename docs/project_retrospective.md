## 2. 当前架构概览

```
api（HTTP）  →  app（用例编排）  →  domain / core（规则与端口）  ←  infra（适配器）
                        ↑
              api/container.py（唯一组装根）
```

依赖规则与验证结果：

| 规则 | 验证结果 |
|---|---|
| `api` 只在 `container.py` import `infra` | ✅ |
| `app` / `domain` / `core` 不 import `infra`、`config` | ✅ |
| `domain` / `infra` / `core` 不 import `app` / `api` | ✅ |
| `app` 不 import `fastapi` / `starlette` / `sqlite3` | ✅ |
| 路由不直接接触队列、限流器 | ✅ |
| parser 构造只在 `infra/parsers.py` | ✅ |
| `core` 依赖边界测试（禁止框架与跨层） | ✅（允许 pydantic） |

核心链路只有一条：

```
POST /contracts
  → 限流 → 队列准入 → 上传校验 → SHA-256 去重 → 落盘
  → 抢占解析 → 后台解析/清洗 → 写产物
  → 读取 cleaned_text → 审查排队 → 规则 + LLM + 验证 + 合并
  → 结果持久化 → 轮询 /result 或查看 /report
```

## 5. 问题与风险

### P0：上线前必须解决

**P0-1 多进程状态不共享**

- 证据：`app/review_queue.py` 的 `_tasks` 是进程内字典；`BoundedSemaphore`、`SlidingRateLimiter` 的事件表同样在进程内。
- 后果：`uvicorn --workers N` 时，`/result`、`/report` 可能返回 404；限流与准入按进程放大；SQLite 并发写可能 `database is locked`。
- 当前定位：适合单进程部署。需要明确写进 README 或启动检查。

**P0-2 没有鉴权**

- 证据：`src/` 内未发现 `Authorization` / API Key / CORS 相关代码。
- 后果：能访问端口的人可以上传、删除合同、下载清洗文本、查看完整审查报告。合同属于敏感数据。

**P0-3 非 `ParsingError` 会让合同卡在 `parsing`**

- 证据：`app/parsing_service.py` 的 `execute` 只捕获 `ParsingError`；若 `write_artifacts` 抛 `OSError` 等，异常继续上抛。
- 后果：`UploadPipeline.process` 会把审查标记失败并重新抛出，但合同状态仍是 `parsing`，只有重启时的 `recover_interrupted_parsing` 才会转 `failed`。
- 修复方向：`execute` 的兜底分支把任何异常都落成 `failed`（记录错误后返回），或由 `UploadPipeline.process` 在异常时更新合同状态。

**P0-4 大文件先读入内存再校验**

- 证据：`routes/contracts.py` 的 `content = await file.read()`；批量为每个文件 `await upload.read()`，之后才在 pipeline 里校验单文件大小/总大小。
- 后果：超大请求会先占用内存，再被拒绝。
- 修复方向：读取前用 `Content-Length` 快速拒绝；批量改为流式读取并逐文件校验。

**P0-5 真实环境未验证**

- 证据：全量测试使用 `FakeLLM`；MinerU 本地服务、DeepSeek 真实调用未在本轮跑过。
- 后果：协议、超时、解析产物格式、限流阈值都只在假实现上验证过。

### P1：重要但可排期

1. **缺少手动开始审查接口**：审查失败后无法重试；重新上传被 SHA-256 去重挡住。
2. **手动重新解析不重跑审查**：`POST /contracts/{id}/parse` 以 `enqueue_review=False` 运行；重新解析后旧审查结果仍挂在合同上。
3. **审查 TTL 只清理终态**：`queued` 任务不会过期，只能靠准入上限兜底；长期占坑的任务会一直排队。
4. **日志无轮转、trace 无保留策略**：`logging_setup` 使用普通 `FileHandler`；trace 目录只增不减。
5. **缺少健康检查与指标**：只有 `/stats`，没有 `/healthz`、延迟/错误率指标。
6. **无 CI / 无静态检查**：ruff、mypy 均未接入；依赖边界测试是目前唯一的自动架构约束。
7. **没有速率限制的跨进程一致性**（与 P0-1 同源）。

### P2：结构打磨

1. `api/schemas.py` 未抽出，批量响应模型仍在路由文件里。
2. `domain/verifier.py`、`domain/merge/merger.py` 直接写日志，属于观测性耦合；可改为返回 `dropped`/`trace_out`。
3. `AppContainer.validator` 字段目前无外部消费者，属于可清理的死状态。
4. `domain/ports.py` 同时承载领域端口与技术端口（LLM/限流/Trace/审查仓储），严格拆分可放到 `app/ports.py`。
5. `review_tasks` 表列名仍是 `task_id`（已注释说明），与领域名 `contract_id` 不一致。
6. `offline_batch` 与 HTTP 管线是两条入口，但已共用 `parse_and_clean`，重复度可控。

## 7. 过程复盘

两件值得记录的插曲：

1. **批量 `sed -i` 重写换行符**：一次跨目录的批量替换把未改动文件的 CRLF/LF 重写，`git status` 出现大量假改动。已全部恢复，但教训是：批量修改应限制在确认过的文件清单内，并优先用 `Read/Edit` 或保持 `newline=""` 的脚本。
2. **`src/` 目录曾整体消失**：工作区被外部操作删除并暂存，未提交改动丢失。随后从会话记录中的 diff 与测试反向重建。教训：每阶段提交，避免长时间保留大量未提交改动。

## 9. 总体结论

- **架构层面**：关注点分离、依赖方向、单一入口、数据单向流动都已落地，并且有可执行的验收方式。这轮重构的主要目标已经达成。
- **工程层面**：输入校验、去重、限流、准入、并发控制、恢复、取消、日志、trace、测试都具备；缺的是 CI、静态检查与生产运维能力。
- **生产就绪层面**：当前是一个**高质量的单进程服务**，不是可水平扩展的多实例服务。上线前需要补鉴权、资源保护、真实环境验证，并明确部署模型。

一句话：**结构已经干净；接下来要补的是“能不能安全、稳定地对外提供服务”，而不是继续拆文件。**
