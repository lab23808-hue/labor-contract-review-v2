## 2. 拐点与归因

**拐点在 N=8。** 总耗时从 22.92s（N=1）降到 4.86s（N=8），之后不再改善：
N=16 反而升到 5.88s，N=32 为 5.26s。p50 从 1.24–1.45s（N=1–4）升到
2.41s（N=8）和 4.34–4.59s（N=16–32）。

归因：

1. **不是本地 CPU**：系统 CPU 平均 46.8–55.6%，峰值 69.3–79.4%，12 个逻辑 CPU
   没有饱和；N=8 之后吞吐不再增长时 CPU 也没有继续上升。批处理大部分时间在等
   API。
2. **不是线程切换/GIL**：如果线程开销主导，N=16/32 应该更差且 CPU 升高；实际
   只是 p50 变长、总耗时基本持平，符合排队而不是计算争用。
3. **主要瓶颈是客户端主动节流 + API 等待**：`max_inflight=8` 把在途请求压在
   8 个，`rps=8` 限制启动速率。N>8 的额外线程在信号量上排队，所以总耗时不再
   下降，p50 上升。N=8 正好等于 max_inflight，是当前配置的膝点。
4. **本窗口内服务商没有触发 429/60s 空响应**：六档全部 0 失败、0 重试，说明
   8 并发的主动节流把请求压在了安全区。要观察服务商真实上限，需要单独做
   max_inflight=12/16 的对照实验，不能把当前数据当作线程模型上限。

## 4. 故障注入结果

`--chaos --chaos-rate 0.25 --workers 4`：

| 指标 | 值 |
|---|---:|
| 处理文件 | 16 |
| ok | 14 |
| llm_failed | 2（G-14、G-16） |
| error（抛异常） | 0 |
| GT 命中 | 16/16 |
| 总耗时 | 10.30s（含退避的 wall time 19.55s） |
| total_tokens | 14,682 |

日志中的重试原因包括 `invalid_json`、`connection`、`timeout`，退避
1.0–1.4s；每份最多 2 次尝试，没有递归放大。G-14、G-16 两次尝试都命中
chaos，最终 `llm.failed`，但规则仍分别报出 `noncompete_no_pay` 和
`social_security_missing`，所以 GT 不受影响，整批没有中断。

### 排查路径（实际演练）

1. 从 chaos batch 的 `batch.item_failed` 事件直接定位两份：G-14、G-16。
2. 打开 `logs/review_batch_<run_id>.log`，看到 `llm.retry` 的 reason 序列
   和最终的 `llm.failed`（G-14 最后一次是 `timeout`，G-16 是 `invalid_json`）。
3. 打开 `trace_<run_id>/14_G-14/05_llm_raw.json` / `06_llm_verified.json`：
   `llm_failed=true`，`error=timeout`，usage 全 0；`08_final_report.json` 的
   `meta.llm_failed=true` 但仍有 `noncompete_no_pay`（rules）。
4. 同样的路径检查 G-16，得到 `social_security_missing`（rules）。
5. 结论：故障发生在 LLM 分支，不在解析/规则/合流；批处理捕获了失败项，
   规则侧兜底成功。

已知 logging 限制：`llm.retry` / `llm.failed` 事件本身不带文件名（多线程
交织），需要靠 `batch.item_failed` 或 per-item trace 反查。若 M14 要做实时
按文件归因，需要给日志加线程本地的 item context。

## 6. M14 方向建议

当前同步线程模型在 `max_inflight=8` 处到顶，且 CPU 没有饱和；这不是 asyncio
能自动解决的问题。建议 M14 先做**受控的 max_inflight 扫描**（8/12/16），
保持 16 份语料和相同 rps 上限，观察：

- 服务商是否开始返回 429、60s 空响应或明显变慢；
- 吞吐是否还能线性增长；
- 如果 max_inflight 提到 16 仍稳定，再评估 asyncio 是否值得；
- 如果服务商先降级，换 asyncio 只会更快撞墙，应优先考虑配额/多 key/请求合并。

在拿到这组数据前，不建议重写为 asyncio。

## 7. M14 真实上限扫描（2026-11-03 补测）

### 方法

- 任务数：32（16 份语料各复制一份），这样 inflight=24/32 才能真正达到；
  每份语料的 GT 不变，重复副本按同一 base 名对照。
- `workers = max_inflight`，消除 worker 队列干扰。
- `rps=64`，令牌桶形同不限。
- 四档：8 / 16 / 24 / 32；真实 DeepSeek 调用，无 `--trace`。
- 原始数据：`tests/stress/limit_scan.json`。

### 对比表

| 8 | 32 | 9.47 | 3.38 | 1.48 | 4.48 | 4.51 | 0 | 0 | 0 | 0 | 0 | 0 | 73.0 / 89.0% | 33,728 | 32/32 |
| 16 | 32 | 6.43 | 4.98 | 3.12 | 5.01 | 5.15 | 0 | 0 | 0 | 0 | 0 | 0 | 74.1 / 91.2% | 33,556 | 32/32 |
| 24 | 32 | 7.04 | 4.54 | 5.37 | 5.70 | 5.78 | 0 | 0 | 0 | 0 | 0 | 0 | 71.8 / 85.9% | 33,663 | 32/32 |
| 32 | 32 | 6.08 | 5.26 | 5.26 | 5.79 | 6.02 | 0 | 0 | 0 | 0 | 0 | 0 | 68.8 / 86.8% | 33,590 | 32/32 |

每档日志都有 32 条 `llm.call_done`，没有 `llm.retry` / `llm.call_failed` /
`llm.failed`；tokens 均为 33.5–33.7k，约 1,050/份。

### 结论

**按本轮判据，真实上限（延迟口径）是 inflight=16。**

证据：p50 从 inflight=8 的 1.48s 翻倍到 3.12s（2.1x），这是第一次
「明显翻倍」；此后 24/32 的 p50 稳定在 5.3s 左右，没有继续线性恶化。

但必须同时记录：

1. **没有错误上限信号**：8/16/24/32 全部 0 重试、0 空响应、0 429、
   0 llm_failed。M13 背景提到的「60s 静默降级」在这 32 并发窗口内
   没有出现，服务商的错误上限 >32。
2. **吞吐还在涨，只是延迟变差**：32 的吞吐 5.26/s 是本轮最高，比 8 的
   3.38/s 高 56%，但 p50 从 1.48s 涨到 5.26s（3.6x）。这是延迟拐点，
   不是错误拐点。
3. **不是本地 CPU 打满**：CPU 平均 68.8–74.1%，峰值 85.9–91.2%，12 核
   没有完全饱和；p50 在 16 就翻倍，而 24/32 的 CPU 平均反而略低，
   说明主因是 API 侧延迟/排队，不是本地计算。
4. 24 档吞吐 4.54/s 略低于 16 档 4.98/s，p50 却更高；结合 32 档恢复到
   5.26/s，更像是服务商延迟波动，而不是稳定的 24 并发上限。

### 对 M14 方向的回答

- 延迟敏感场景：cap 在 **8–16**。8 是保守档，16 是 p50 开始翻倍的拐点。
- 吞吐优先场景：**32 可用**，但 p50 约 5.3s，是 8 档的 3.6 倍；
  如果业务能接受这个延迟，当前线程模型足够，不需要 asyncio。
- 如果继续找**错误**上限，需要把任务数加到 48/64，再扫 32/48/64；
  但延迟会继续主导，收益递减。
- 本轮没有触发 429/空响应，因此「服务商在 XX 并发开始静默降级」的
  结论还不能下；只能说到 **32 并发仍未出现错误信号**。

## 8. 并发专题结论（M15 定版）

这一节回答三个问题，也是这条并发学习线的收尾。

### 8.1 瓶颈是什么

**API 等待，不是本地 CPU，也不是线程切换。**

- M13 六档 CPU 平均 46.8–55.6%，峰值 69.3–79.4%；M14 四档 CPU 平均
  68.8–74.1%，峰值 85.9–91.2%。12 个逻辑 CPU 始终没有被打满。
- 并发上升时 p50 从 1.24s 涨到 5.26s，但 CPU 没有同步逼近 100%；
  p50 在 16 就翻倍，而 24/32 的 CPU 平均反而略低。这说明时间花在等
  API，而不是算。
- 线程切换/GIL 没有成为主导：如果线程开销主导，吞吐应在 N>8 后下降
  且 CPU 升高；实际 M14 的 32 档吞吐仍是最高（5.26/s），只是 p50 变差。
- 批处理进程的主要工作是拼 prompt、解析 JSON、规则判断，这些在总耗时
  里占比很小；日志里的 `llm.call_done.elapsed` 解释了绝大部分单份时间。

### 8.2 上限在哪

| 口径 | 数值 | 证据 |
|---|---|---|
| 延迟拐点 | **inflight=16** | p50 从 1.48s（8）翻倍到 3.12s（16），2.1x；24/32 稳定在 ~5.3s |
| 吞吐峰值 | inflight=32 | 5.26/s，比 8 档 3.38/s 高 56%；但 p50 是 8 档的 3.6 倍 |
| 错误上限 | **>32，本轮未触达** | 8/16/24/32 全部 0 重试、0 空响应、0 429、0 llm_failed |
| 服务商静默降级 | 本轮未出现 | 没有 60s 空响应；错误信号要等 48/64 任务扫描才能继续找 |

所以：**想要低延迟，cap 在 8–16；想要吞吐，32 可用但 p50 约 5.3s；
服务商的错误上限至少高于 32。** 24 档的吞吐略低于 16、p50 更高，更像
服务商延迟波动，不作为稳定上限。

### 8.3 为什么不上 asyncio

因为线程开销不是瓶颈，换了不会更快：

1. 当前同步线程模型在 32 并发下仍然 0 错误，吞吐比 8 档高 56%；CPU
   平均不到 75%，没有出现线程/ GIL 导致的吞吐崩塌。
2. p50 的增长来自 API 侧延迟和排队，asyncio 只能改变本地等待方式，
   不能降低服务商每次请求的耗时。
3. 若未来要冲 48/64 以上，第一步也应是先测服务商错误上限；如果服务商
   先降级，async 只会更快撞墙，应先考虑配额、多 key、请求合并。
4. 因此本轮不引入 asyncio、不重构。当前线程模型 + 令牌桶 +
   `max_inflight` 已经足够覆盖 8–32 的实际场景。

### 8.4 定版配置

| 场景 | 建议 | 吞吐 | p50 |
|---|---|---|---|
| 默认 / 延迟友好 | `--workers 8 --max-inflight 8` | ~3.4/s（32 任务） | ~1.5s |
| 平衡 | `--workers 16 --max-inflight 16` | ~5.0/s | ~3.1s |
| 吞吐优先 | `--workers 32 --max-inflight 32` | ~5.3/s | ~5.3s |

CLI 默认 `--max-inflight 8`、`--rps 8`；`--max-inflight` 的 help 已写明
「默认 8（延迟友好）；批量吞吐可调到 32（M14：吞吐 +56%，p50 约 3.6 倍）」。
